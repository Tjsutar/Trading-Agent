## 3. Functional Requirements

### 3.1 Market Data Layer

#### FR-MD-001: Multi-Broker Integration
- **Priority:** Critical
- **Description:** System must connect to MetaTrader 5 (MT5) for live market data
- **Acceptance Criteria:**
  - Fetch OHLCV data for timeframes: M1, M5, M15, H1, H4, Daily
  - Support assets: XAUUSD, EURUSD, USDJPY, Nifty 50, Bank Nifty
  - Handle connection failures with auto-reconnect (max 3 retries, 5s intervals)
  - Store raw tick data in PostgreSQL with partitioning by date

#### FR-MD-002: Historical Data Access
- **Priority:** High
- **Description:** Retrieve minimum 1 year of historical data for backtesting
- **Acceptance Criteria:**
  - Data completeness > 99.5% (handle missing candles gracefully)
  - Store in PostgreSQL with BRIN indexes on timestamp columns for fast range queries
  - Update daily with new candles via scheduled job
  - Support data export to CSV/Parquet for external analysis

#### FR-MD-003: Data Quality Monitoring
- **Priority:** High
- **Description:** Detect and alert on data anomalies (gaps, spikes, duplicates)
- **Acceptance Criteria:**
  - Identify candle gaps > 5 minutes during trading hours
  - Flag price spikes > 3 standard deviations from moving average
  - Remove duplicate timestamps before storage
  - Log all anomalies to PostgreSQL audit table

### 3.2 Analysis Layer

#### FR-AL-001: Liquidity Detection
- **Priority:** Critical
- **Description:** Identify Equal Highs (EQH) and Equal Lows (EQL) as liquidity pools
- **Acceptance Criteria:**
  - Calculate price tolerance: `|High1 - High2| <= ATR * 0.2`
  - Minimum 2 touches required to qualify as liquidity zone
  - Tag zones with strength score (2-touch = weak, 3+ touch = strong)
  - Store detected zones in PostgreSQL with validity period

#### FR-AL-002: Multi-Timeframe Alignment
- **Priority:** Critical
- **Description:** Confirm higher timeframe bias before lower timeframe entry
- **Acceptance Criteria:**
  - H1 trend determines market bias (bullish/bearish/neutral)
  - M1-M5 used only for precision entry after H1 confirmation
  - Block trades if timeframes conflict (e.g., H1 bearish but M5 long signal)
  - Cache timeframe analysis in Redis with 60-second TTL

#### FR-AL-003: Fake Breakout Detection
- **Priority:** High
- **Description:** Identify institutional traps through wick-to-body ratio analysis
- **Acceptance Criteria:**
  - Calculate ratio: `wick_length / body_length`
  - Flag as fake breakout if ratio > 1.5 and volume < average volume
  - Do NOT enter trades in direction of fake breakout for next 3 candles
  - Persist fake breakout events in PostgreSQL for pattern analysis

#### FR-AL-004: Technical Indicator Library
- **Priority:** Medium
- **Description:** Calculate standard technical indicators for strategy enhancement
- **Acceptance Criteria:**
  - Support: RSI, MACD, Bollinger Bands, ATR, Moving Averages
  - Use TA-Lib library for optimized calculations
  - Cache computed indicators in Redis for reuse across strategies
  - Store daily indicator snapshots in PostgreSQL for backtesting

### 3.3 Strategy Layer

#### FR-SL-001: Trade Signal Generation
- **Priority:** Critical
- **Description:** Generate BUY/SELL signals based on liquidity sweep + market structure
- **Acceptance Criteria:**
  - Signal triggers only when: (1) Liquidity swept, (2) HTF aligned, (3) RR ≥ 1:2
  - Include entry price, stop loss, and 2 take-profit levels
  - Log signal generation timestamp with millisecond precision to PostgreSQL
  - Publish signal to Redis pub/sub channel for Golang execution layer

#### FR-SL-002: Position Sizing Algorithm
- **Priority:** Critical
- **Description:** Calculate lot size based on risk percentage and volatility
- **Acceptance Criteria:**
  - Risk = 1% of capital per trade (configurable per strategy)
  - Adjust for volatility: if India VIX > 25, reduce size by 50%
  - Never exceed broker's maximum position limit
  - **Formula:** `Lot Size = (Account Balance * Risk%) / (Stop Loss Distance * Point Value)`
  - Store position sizing calculations in PostgreSQL for audit

#### FR-SL-003: Strategy Configuration Management
- **Priority:** High
- **Description:** Support multiple strategies with independent parameters
- **Acceptance Criteria:**
  - Store strategy configs in PostgreSQL (name, parameters, status, version)
  - Enable/disable strategies without system restart
  - Version control for strategy parameters with rollback capability
  - Support A/B testing by allocating capital percentage to each strategy

### 3.4 Execution Layer

#### FR-EX-001: Order Placement
- **Priority:** Critical
- **Description:** Execute market/limit orders via broker API with ultra-low latency
- **Acceptance Criteria:**
  - Latency: signal-to-order < 100ms
  - Include stop loss and take profit in initial order (bracket order)
  - Retry failed orders max 2 times with exponential backoff
  - Write order acknowledgment to PostgreSQL immediately after broker confirmation
  - Update order status in Redis for real-time UI sync

#### FR-EX-002: Breakeven Stop Loss Management
- **Priority:** High
- **Description:** Move stop loss to breakeven when price reaches configured RR threshold
- **Acceptance Criteria:**
  - Monitor open positions every 1 second via Redis state
  - Modify SL to entry +/- spread when configured trigger is hit (default: 50% of TP1)
  - Log all modifications to PostgreSQL with before/after price levels
  - Maintain modification history for compliance and audit
  - Configuration per strategy: `{breakeven_enabled: true, breakeven_trigger_rr: 1.0}`

#### FR-EX-005: Trailing Stop Loss Management
- **Priority:** Medium
- **Description:** Dynamically adjust stop loss to follow profitable price movement and maximize winning trades
- **Acceptance Criteria:**
  - Activate trailing SL after price moves X pips in profit (configurable per strategy)
  - Trail at Y pips distance from current price (configurable, default: 15 pips for Forex, ₹10 for indices)
  - Once activated, SL only moves in profitable direction (never widens or reverses)
  - Track maximum favorable price reached in Redis: `position:{order_id}:max_favorable_price`
  - Update SL via broker API when new trailing level calculated
  - Store trailing SL state in PostgreSQL trade record: `trailing_sl_enabled`, `trailing_activation_price`, `max_profit_reached`
  - Log all trailing SL adjustments with timestamp, old SL, new SL, and current price
  - Support three trailing modes: (1) Fixed pips distance, (2) ATR-based distance, (3) Percentage-based
  - Configuration per strategy: `{trailing_enabled: true, activation_pips: 20, trail_distance_pips: 15, trail_mode: "fixed"}`
  - If both breakeven and trailing enabled: activate breakeven first, then switch to trailing after activation threshold
  - Include trailing SL visualization in dashboard with price path and SL adjustments

#### FR-EX-003: Session Management
- **Priority:** Critical
- **Description:** Maintain active broker session without manual intervention
- **Acceptance Criteria:**
  - Proactively renew authentication token 5 minutes before expiry
  - Detect "invalid session" errors and auto-relogin
  - Alert admin if relogin fails after 3 attempts
  - Store session status and health checks in Redis
  - Log all session events to PostgreSQL audit table

#### FR-EX-004: Order Reconciliation
- **Priority:** High
- **Description:** Ensure local state matches broker account state
- **Acceptance Criteria:**
  - Query broker API every 5 minutes for open positions
  - Compare with local PostgreSQL records
  - Flag discrepancies (orphaned orders, missing fills)
  - Auto-correct minor discrepancies, alert admin for major ones

### 3.5 Monitoring & Risk Layer

#### FR-MR-001: Kill Switch (Daily Loss Cap)
- **Priority:** Critical
- **Description:** Automatically halt all trading if daily loss exceeds threshold
- **Acceptance Criteria:**
  - Default cap: 2% of starting daily capital (e.g., ₹2,000 on ₹1,00,000)
  - Close all open positions immediately when cap hit
  - Block new trades until next trading day
  - Send emergency notification (email/SMS/Telegram)
  - Record kill switch activation in PostgreSQL with full context

#### FR-MR-002: Risk-Reward Filter
- **Priority:** Critical
- **Description:** Block trades that do not meet minimum RR criteria
- **Acceptance Criteria:**
  - Minimum RR = 1:2 (configurable per strategy)
  - Calculate RR before order placement: `(TP - Entry) / (Entry - SL)`
  - Log rejected trades with reason "RR below threshold" to PostgreSQL
  - Maintain daily rejection statistics in Redis for dashboard

#### FR-MR-003: Safety Gatekeeper
- **Priority:** High
- **Description:** Verify margin availability before every trade
- **Acceptance Criteria:**
  - Query broker API for available margin
  - Require 10% buffer above required margin
  - Reject trade if buffer not available
  - Log all margin checks to PostgreSQL
  - Alert if margin utilization exceeds 80%

#### FR-MR-004: Real-Time Dashboard
- **Priority:** Medium
- **Description:** Display system status, P&L, and open positions
- **Acceptance Criteria:**
  - Update every 2 seconds via WebSocket (data from Redis)
  - Show: Current Equity, Daily P&L, Open Positions, Win Rate, Sharpe Ratio
  - Visual alerts for kill switch activation or system errors
  - Historical charts powered by PostgreSQL aggregations
  - Support filtering by strategy, asset, and date range

#### FR-MR-005: Performance Analytics
- **Priority:** Medium
- **Description:** Calculate and display key performance metrics
- **Acceptance Criteria:**
  - Compute: Sharpe Ratio, Sortino Ratio, Max Drawdown, Win/Loss Ratio
  - Calculate metrics daily and store in PostgreSQL
  - Compare current month vs previous months
  - Generate equity curve from PostgreSQL trade history
  - Export performance reports to PDF

### 3.6 State Persistence & Data Management

#### FR-SP-001: Trade Database Schema
- **Priority:** Critical
- **Description:** Persist all trade data in PostgreSQL with optimal schema design
- **Acceptance Criteria:**
  - Tables: `trades`, `orders`, `signals`, `strategies`, `accounts`, `audit_logs`
  - Use partitioning on `trades` table by month for performance
  - Include indexes on: `symbol`, `strategy_id`, `entry_time`, `exit_time`
  - Enforce foreign key constraints for data integrity
  - Store all timestamps in UTC with timezone support

#### FR-SP-002: Redis Cache Strategy
- **Priority:** High
- **Description:** Use Redis for real-time state and performance optimization
- **Acceptance Criteria:**
  - Cache: Open positions, latest prices, indicator values, account balance
  - Use Redis Streams for signal communication (Python → Golang)
  - Set appropriate TTLs (positions: no expiry, prices: 60s, indicators: 300s)
  - Implement cache invalidation on order fills
  - Use Redis pub/sub for WebSocket broadcasting to UIs

#### FR-SP-003: Configuration Management
- **Priority:** High
- **Description:** Store all system and strategy parameters in PostgreSQL
- **Acceptance Criteria:**
  - Table: `configurations` with key-value pairs and versioning
  - Support parameter types: string, integer, float, boolean, JSON
  - Load configurations on startup with validation
  - Implement hot-reload for non-critical parameters
  - Maintain configuration change history with user attribution

#### FR-SP-004: Data Backup & Recovery
- **Priority:** Critical
- **Description:** Ensure zero data loss with automated backups
- **Acceptance Criteria:**
  - PostgreSQL automated backups every 6 hours
  - Retain backups for 30 days
  - Test recovery process monthly
  - Backup to separate physical location (cloud storage)
  - Document recovery procedures with RTO < 1 hour

#### FR-SP-005: Database Performance Optimization

### 5.3 Communication Protocols

**Python Analysis ↔ Golang Execution:**
- **Signal Passing:** Redis Streams (XADD/XREAD)
- **Configuration Sync:** PostgreSQL read on startup, Redis pub/sub for hot reload
- **Data Sharing:** PostgreSQL for historical, Redis for real-time

**Golang API ↔ UI (Angular 21+ / React Native):**
- **GraphQL Queries:** HTTP POST to `/graphql` endpoint
  - Dashboard data fetching
  - Complex analytics queries
  - Nested data retrieval (trades with SL modifications)
- **GraphQL Mutations:** HTTP POST to `/graphql` endpoint
  - Strategy configuration updates
  - Kill switch toggle
  - Manual position closure
- **GraphQL Subscriptions:** WebSocket to `/graphql` endpoint
  - Real-time position updates
  - Live P&L changes
  - Alert notifications
  - SL modification events
- **REST API:** HTTP to `/api/v1/*` endpoints
  - Order execution (POST /api/v1/orders)
  - Health checks (GET /api/v1/health)
  - System metrics (GET /api/v1/metrics)

**All Components ↔ PostgreSQL:**
- **Connection Pooling:** PgBouncer (transaction mode)
- **ORM:** SQLAlchemy (Python), pgx (Golang)
- **Migrations:** Alembic (Python) or golang-migrate

**All Components ↔ Redis:**
- **Client Libraries:** redis-py (Python), go-redis (Golang)
- **Connection:** Single TCP connection per process with automatic retry

### 5.4 Data Flow for Trade Execution

1. **Market Data Ingestion (Continuous):**
   - MT5 → Golang data fetcher → PostgreSQL (historical) + Redis (latest)

2. **Signal Generation (Every candle close):**
   - Python reads from Redis (latest prices) + PostgreSQL (historical)
   - Computes liquidity zones, MTF alignment, fake breakouts
   - Generates signal → Redis Stream (channel: `signals`)

3. **Signal Validation & Execution:**
   - Golang execution service reads from Redis Stream
   - Validates: RR ratio, margin, kill switch status
   - If valid → Place order via MT5 API
   - Write to PostgreSQL: `orders`, `trades`
   - Update Redis: `open_positions` hash

4. **Position Monitoring:**
   - Golang monitors Redis `open_positions` every 1 second
   - Checks for: TP1 hit, breakeven trigger, trailing SL activation, trailing SL adjustment
   - **Breakeven Logic:** If `breakeven_enabled` and profit ≥ `breakeven_trigger_rr`, move SL to entry ± spread
   - **Trailing SL Logic:** 
     - Track max favorable price in Redis: `position:{order_id}:max_favorable_price`
     - If `trailing_enabled` and profit ≥ `activation_pips`, activate trailing
     - Once active, continuously update SL based on: `new_sl = max_favorable_price - trail_distance`
     - For BUY: SL only moves UP, for SELL: SL only moves DOWN
   - Modifies orders via MT5, updates PostgreSQL (`trades` table + `sl_modifications` table) + Redis
   - Publishes SL modification events to Redis pub/sub: `sl_modifications` channel

5. **UI Updates:**
   - Golang publishes events to Redis pub/sub channel: `ui_updates`
   - Angular/React Native subscribes via WebSocket
   - Dashboard renders live P&L, positions, equity curve

# Live positions (Hash)

risk:kill_switch → "ACTIVE" | "INACTIVE"

# Signal queue (Stream)
signals → [{signal_id, type, symbol, entry, sl, tp, rr, timestamp}]

# Cache for indicators (Hash with TTL 300s)
indicators:{symbol}:{timeframe} → {rsi, macd, bb_upper, bb_lower, atr}

# Session status (String with TTL)
session:mt5 → {status, token_expiry, last_heartbeat}

position:{order_id}:max_favorable_price → DECIMAL value (highest for BUY, lowest for SELL)
position:{order_id}:trailing_state → {activated: bool, last_update: timestamp}

PUBLISH sl_modifications → Real-time SL change notifications

## 8. Risks & Mitigation

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| PostgreSQL performance degradation | Medium | High | Use partitioning, BRIN indexes, regular VACUUM; archive old data |
| Redis data loss (if not persistent) | Medium | Critical | Enable AOF persistence, use Redis replication for HA |
| Overfitting to backtest data | High | Critical | Walk-forward analysis, out-of-sample testing, 70/30 train/test split |
| Broker API downtime | Medium | High | Implement exponential backoff retry, maintain local order state |
| Slippage in live vs demo | High | Medium | Test during volatile sessions, adjust RR expectations, use limit orders |
| Session token expiry | Medium | Critical | Proactive renewal 5 min before expiry, store expiry in Redis |
| Kill switch fails to trigger | Low | Critical | Unit tests with 100% coverage, manual override button in UI |
| Database connection pool exhaustion | Low | High | Monitor pool usage, implement circuit breaker, scale pool size |
| Message loss in Redis Streams | Low | Medium | Use consumer groups with acknowledgments, set retention policy |

## 9. Assumptions & Constraints

### 9.1 Assumptions
Assumptions are conditions accepted as true for planning purposes. If these prove false, the project may require re-evaluation:

**Business Assumptions:**
- Broker API (MetaTrader 5) remains stable, free to use, and accessible for retail traders
- User has minimum ₹1,00,000 capital for meaningful position sizing and risk management
- User will dedicate 2-4 hours daily for system monitoring during Phase 1-3 (development)
- Market conditions remain within historical volatility ranges (India VIX typically 15-30)
- Prop firm rules and regulations remain consistent during development period

**Technical Assumptions:**
- PostgreSQL hosted on reliable infrastructure (cloud VPS or local machine with UPS backup)
- Network latency to broker server < 50ms for order execution
- Internet connection maintains 99%+ uptime during market hours
- Python 3.11+, Golang 1.21+, PostgreSQL 15+, Redis 7+, Angular 21+ remain stable and supported
- Open-source libraries (pandas, numpy, TA-Lib, gqlgen) continue free availability
- GraphQL and REST API standards remain compatible with future versions

**Resource Assumptions:**
- User has sufficient technical expertise in Python basics (or willingness to learn)
- Development environment available (laptop/desktop with minimum 8GB RAM, 4-core CPU)
- Access to historical market data (minimum 1 year of OHLCV data for backtesting)
- Availability of development tools (VS Code, Git, Docker) without licensing costs

**Market & Regulatory Assumptions:**
- No major regulatory changes restricting algorithmic trading in target markets
- Broker continues to allow API-based automated trading
- No introduction of transaction taxes that make strategy unprofitable
- Market structure (liquidity pools, institutional behavior) remains predictable

### 9.2 Constraints
Constraints are limitations that cannot be changed and must be worked within:

**Budget Constraints:**
- **Development Budget:** ₹0 for software licenses (100% open-source stack)
- **Infrastructure Budget:** Maximum ₹1,000/month for VPS hosting (Phase 4 only)
- **Live Trading Capital:** Start with ₹10,000-₹25,000 in Phase 4 (small capital constraint)
- **No External Funding:** Self-funded project, cannot hire developers or purchase premium services
- **Tool Costs:** Limited to free tiers of monitoring tools (Grafana, Prometheus)

**Timeline Constraints:**
- **Fixed Deadline:** 6 months to reach Phase 4 (live deployment)
- **Knowledge Cutoff:** Must learn Python, Golang, GraphQL, PostgreSQL within Phase 1-2
- **Market Hours:** Development/testing limited to non-market hours (9:15 AM - 3:30 PM IST unavailable)
- **Backtesting Data:** Historical data limited to what's freely available via MT5 (typically 1-2 years)

**Technology Constraints:**
- **No High-Frequency Trading:** Retail internet latency (20-100ms) prevents HFT strategies
- **Broker API Limitations:** 
  - MT5 API rate limits (typically 10 requests/second)
  - No direct market access (DMA) - orders routed through broker
  - Limited asset coverage (only symbols offered by broker)
- **Database Size:** PostgreSQL limited by VPS disk space (typically 50-100GB on budget VPS)
- **Compute Resources:** 
  - Local development limited to personal laptop/desktop specifications
  - Cannot afford dedicated GPU for ML-based strategies
  - Backtesting speed constrained by single-machine processing

**Skill & Resource Constraints:**
- **Solo Developer:** No team available for code review, testing, or 24/7 monitoring
- **Learning Curve:** Must learn new technologies (Golang, GraphQL, PostgreSQL) during development
- **Time Availability:** Limited to evenings/weekends for development (2-4 hours/day)
- **No DevOps Expertise:** Infrastructure setup and deployment must be simple (no Kubernetes initially)

**Regulatory & Compliance Constraints:**
- **Prop Firm Rules:** Must comply with evaluation rules (max 10% profit target, 5% daily drawdown limit)
- **Tax Implications:** Must maintain complete trade logs for tax reporting (7-year retention in India)
- **Data Privacy:** Cannot store other users' data (single-user system only in Phase 1-3)
- **KYC Requirements:** Broker account subject to KYC verification and withdrawal limits

**Market Constraints:**
- **Trading Hours:** Limited to exchange hours (9:15 AM - 3:30 PM IST for NSE, 24/5 for Forex)
- **Liquidity:** Strategy effectiveness depends on available market liquidity (low-liquidity assets excluded)
- **Slippage:** Expected 2-5 pips slippage during volatile periods (cannot eliminate)
- **Spread Costs:** Broker spreads reduce profitability (typically 1-3 pips for major pairs)
- **Minimum Lot Sizes:** Broker-enforced minimum trade sizes may prevent micro-position sizing

**Operational Constraints:**
- **Uptime Dependency:** System requires constant internet and power (no mobile fallback in Phase 1-3)
- **Single Point of Failure:** No redundancy for database, execution engine, or broker connection initially
- **Manual Intervention Required:** Kill switch activation, system restarts, and error recovery need manual action
- **No 24/7 Monitoring:** System runs unattended during sleep hours (risk of overnight gaps)

**Scalability Constraints:**
- **Maximum Concurrent Pairs:** Limited to 5-10 trading pairs due to compute/API rate limits
- **User Limit:** Single-user system in Phase 1-3 (multi-user architecture not planned)
- **Geographic Restriction:** Hosted in India (latency to non-Indian brokers may be high)
- **Data Retention:** Archive old data after 2 years to manage database size

**Integration Constraints:**
- **Broker Lock-in:** Initially designed for MT5 only (other brokers require adapter development)
- **No Third-party APIs:** Cannot afford paid data feeds (Bloomberg, Reuters) or premium indicators
- **Limited Alert Channels:** Notifications limited to email/Telegram (no SMS due to cost)
- **No Cloud AI:** Cannot use paid AI services (OpenAI, AWS SageMaker) for signal enhancement

**Performance Constraints:**
- **Order Execution Latency:** Target < 100ms, but subject to broker server response time
- **Database Query Speed:** Limited by VPS specifications (cannot guarantee < 100ms for complex queries)
- **Dashboard Concurrency:** Maximum 50 concurrent users (Angular + GraphQL capacity on budget VPS)
- **Backtest Speed:** Limited to ~1000 candles/second due to single-threaded Python execution
